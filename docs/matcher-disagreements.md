# Matcher disagreements

`bun run validate-matcher` runs the hand-written matcher in `src/matcher/match.ts` and osv-scanner over every lockfile under `benchmark/cases`, `src/lockfile/fixtures` and `src/matcher/fixtures/boundary-cases` against the advisory subset under `benchmark/fixtures/advisories`, and prints every entry one matcher reported and the other did not. A package-set difference is a package version only one side saw, which points at a lockfile parsing gap. An advisory-set difference is an advisory group only one side matched for a package version both saw, which points at a range semantics gap.

Every disagreement the command has found is a row below with its ruling. A `fixed` row records a case where the hand-written matcher was wrong and was corrected, so the command no longer prints it. An `accepted` row records a case where the disagreement stands, with the reason. The command reads the accepted rows by the first five columns and exits non-zero on any disagreement without one.


## Notes from the investigation

- Every advisory-set comparison agreed. The boundary lockfiles under `src/matcher/fixtures/boundary-cases` put every subset package at every range event version, one patch above it and a prerelease just below it, 617 versions in all, and the hand-written matcher and osv-scanner 2.7.0 returned the same 5,409 advisory groups. This covers introduced, fixed and last_affected events, versions lists, several ranges per entry, prerelease precedence and withdrawn advisories, which both sides skip.
- osv-scanner only matches a package-lock.json entry that has a `resolved` url. An entry with a version and no `resolved` is reported with `source=LOCAL` in its purl and gets no vulnerabilities, so the boundary lockfile generator writes `resolved` and `integrity` on every entry the way npm does. A real registry entry always has them.
- The package-set rows below are the non-registry specifiers of the lockfile fixtures. The lockfile module keeps a git, file, link or tarball specifier as the version and a workspace package as `workspace:<path>`, and osv-scanner reports a package.json version or an empty version instead. No advisory applies to a non-registry package, so the hand-written matcher looks the version up, finds nothing, and the difference stays accepted. The bun workspace fixture agrees on both sides because osv-scanner keeps the `workspace:` version for bun.lock.
